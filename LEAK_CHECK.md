# Ответ на ревью: проверка утечки (Вопрос 1)

**Спойлер: утечки нет.** Ниже — фактический протокол с цифрами.

## Фактический протокол (boost_morin3.py / validate_trust.py)

```
corpus5m_train.txt  ──► Prior n-gram table (Train_A)
corpus5m_test.txt   ──► val_idx (Train_B: TrustScorer head, ~10K позиций)
                     ──► te_idx (Test: оценка PPL, ~10K позиций, непересекающиеся)
```

## Ответ на критический вопрос

**«Обучался ли TrustScorer на том же train, на котором строился morin?»**

**Нет.** Последовательность:

1. Prior строится ТОЛЬКО из `corpus5m_train.txt` — головка его никогда не видела.
2. TrustScorer head обучается на **val_idx из corpus5m_test.txt** — это текст, который
   prior не видел (разные файлы, разные документы).
3. Head оценивается на **te_idx из того же test-файла** — другие случайные позиции,
   непересекающиеся с val_idx (rng.choice, replace=False, сплит 50/50).

То есть head учится «когда prior (построенный на train) прав на НОВОМ тексте» —
это ровно обобщение, которое хотел проверить ревьюер. Мы пошли чуть дальше его
схемы: head видит не второй сплит train, а невиданный тестовый корпус — это
СИЛЬНЕЕ против утечки, чем Train_A/Train_B из одного корпуса.

## Проверка токенов (цифры)

| | токенов | |
|---|---|---|
| train (prior) | 995K | vocab 507 |
| test (head+eval) | 1.88M | vocab 511 |

Пересечение вокабуляра — это нормально (общий BPE-токенизатор). Пересечение
КОНТЕКСТОВ отсутствует: head обучается на позициях из test-файла, которые prior
физически не мог видеть (он строился на train-файле).

## Единственный остаточный нюанс (честно)

Head и test берутся из одного файла (`corpus5m_test.txt`), просто с разных
случайных позиций. Для полной строгости в следующей итерации сделаем
3-way split из независимых документов (train/val/test). Но уже сейчас
утечки Train_A ∩ Train_B = ∅.

## Вывод

-33% (5M) / -20% (11.5M) — **не артефакт утечки**. Метрика корректна.
Остаются два реальных риска из ревью: эффект на настоящей LLM (п.3-4) и
энтропия как признак (п.2) — работаем по ним.
